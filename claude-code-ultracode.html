Contents
    01 The correction

    It doesn't sit on top of the ladder

    Almost every summary of ultracode calls it "the highest effort level." It isn't one. Claude Code's effort scale has exactly five rungs — low, medium, high, xhigh, max — and ultracode is not a sixth. It's a session setting that pins effort to xhigh and switches on something the ladder has nothing to do with: letting Claude plan and run dynamic workflows on its own.

    ✕ The common mental model

    Implies ultracode > max, and that picking it is only a matter of spending more tokens on reasoning.

    vs
    ✓ What the docs say

    Two separate axes. Ultracode reaches over to the ladder, holds it at xhigh — not max — and adds orchestration beside it.

    Reasoning

    xhigh, every message

    Not max. Ultracode sends xhigh to models that support it; where a model doesn't, the /effort menu doesn't offer ultracode at all.

    Orchestration

    Claude decides to fan out

    Instead of waiting to be asked, Claude plans a workflow for every substantive task — sometimes several in a row for one request.

    Lifetime

    This session only

    It resets when you start a new session, and it can't be written into a settings file or the effort env var.

    02 The effort ladder

    All five rungs, and what each is for

    Effort controls how many tokens Claude spends on the whole response — thinking, prose, and tool calls alike. It is a behavioural signal, not a token budget: at low effort Claude still thinks on genuinely hard problems, just less than it would higher up.

    The bars are ordinal, not measured. They show where a level sits on the scale, nothing more — Anthropic publishes no token multiplier per level, and the scale is calibrated per model, so the same name means different things on different models.

    Which models go how high

    unsupported levels fall back to the highest supported level at or below

    So xhigh requested on Opus 4.6 simply runs as high. Haiku models don't take an effort parameter at all. Because ultracode requires xhigh, it only appears in the /effort menu on the models in the first group.

    03 Three things that sound alike

    max, ultrathink, ultracode

    These get used interchangeably and shouldn't be. One is an effort level, one is a prompt keyword that never touches the API, and one is a session mode.

    Effort level

    max

    The top rung. Deepest reasoning, no ceiling on token spend — and prone to overthinking, with diminishing returns on ordinary work. Session-only unless set through CLAUDE_CODE_EFFORT_LEVEL.

    Changes API
    Yes — sends max
    Scope
    Whole session
    Prompt keyword

    ultrathink

    Type it anywhere in a prompt for deeper reasoning on that turn only. Claude Code adds an in-context instruction — the effort value sent to the API is unchanged. "Think hard" and friends are just ordinary words; only this keyword is recognised.

    Changes API
    No
    Scope
    One turn
    Session setting

    ultracode

    Pins the session to xhigh and lets Claude spin up dynamic workflows unprompted. As a keyword in a single prompt it does something narrower: one workflow for that task, session effort untouched.

    Changes API
    Yes — sends xhigh
    Scope
    Session, or one task
    04 The other half

    What a dynamic workflow actually is

    A dynamic workflow is a JavaScript script that Claude writes to orchestrate subagents at scale. A runtime executes it in the background while your session stays responsive. The script holds the loop, the branching and the intermediate results — so your context window receives only the final answer.

    The shape of a generated script

    plain JavaScript, top-level await
    .claude/workflows/audit-routes.js
    export constmeta = { name: 'audit-routes' }
    const found = await agent('List every .ts file under src/routes/.')
    const audits = await pipeline(found.files, file =>
    agent(`Audit ${file} for missing auth checks.`, { label: file }))
    return audits.filter(Boolean)

    agent() spawns one subagent; pipeline() runs one per item in a list. An agent() call resolves to null if you stop it or it hits an unrecoverable API error — which is why the last line filters. Every run's script is written to a file under ~/.claude/projects/, so you can read it, diff it, or edit it and relaunch.

    Watch one run

    auditing 40 route files · the runtime caps concurrency at 16
    queued running done
    Agents finished0 / 42
    Your context windowholds the final report only

    The point of the second meter. In conversation, every one of those 40 file reviews lands in Claude's context and stays there. In a workflow the results live in script variables, so the context holds one report at the end. That is what lets a run scale past what a single conversation can coordinate.

    05 Switching it on

    Four routes in, and two that don't work

    in a session
    >/effort ultracode
    xhigh effort · workflows on · this session only
    at launch v2.1.203+
    $claude --effort ultracode
    settings flag / agent sdk
    $claude --settings '{"ultracode": true}'
    SDK: applyFlagSettings({ effortLevel: 'ultracode' })
    Won't take it

    The two places ultracode is rejected

    • The persisted effortLevel setting in a settings file. Only low, medium, high and xhigh are accepted there — max and ultracode are session-only by design.
    • The CLAUDE_CODE_EFFORT_LEVEL environment variable. Worse, if it's set to anything other than xhigh, that wins: requests run at the env var's level and ultracode's orchestration stays inactive. Selecting it then just warns you.

    And when workflows are switched off entirely, --effort ultracode quietly degrades to plain xhigh — you get the reasoning, not the orchestration.

    The keyword, which is a different thing

    one workflow for one task, session effort untouched
    a prompt you type
    >ultracode: audit every API endpoint under src/routes/ for missing auth checks

    Asking in plain words — "use a workflow", "run a workflow" — is treated as the same opt-in. Option/Alt + W dismisses the highlight if you didn't mean it.

    Triggers
    • the interactive prompt
    • an IDE extension panel
    • a Remote Control client
    • an Agent SDK app that stamps your keystrokes as human input
    Does not trigger
    • a prompt passed with -p
    • an SDK prompt not marked as human
    • a scheduled task prompt
    • a webhook payload or PR comment relayed into the session

    That last list is a safety boundary, and a recent one: before v2.1.210 the keyword fired from all of those routes too — including text someone else wrote in a pull request comment.

    06 What it costs, and the rails

    Many agents, real money

    A workflow spawns a lot of agents, so one run can use meaningfully more tokens than doing the same task in conversation — and it counts against your plan's usage and rate limits like anything else. The runtime has hard caps; the size guideline is advice.

    Hard cap

    16 concurrent agents

    Fewer on machines with limited CPU cores. Bounds local resource use.

    Hard cap

    1,000 agents per run

    The backstop against a runaway loop, and the thing that bounds the cost of a script gone wrong.

    Advisory

    Large-workflow warning

    Over 25 agents scheduled, or a projected 1.5M tokens, and the task panel flags it. Not shown when ultracode is on — turning it on already opts you into large runs.

    The size guideline

    how many agents Claude aims for · advice to the model, not a cap

    set it v2.1.202+
    >/config workflowSizeGuideline=small

    The resume rule almost everyone gets wrong

    stop a run mid-fan-out, then resume — which agents replay?

    Four agents start in order. You stop the run while B is still going. On resume, cached results stop at the first agent that didn't finish — and everything that started after it re-runs, even if it had already completed.

    07 Judgement

    When to turn it on — and when not to

    Reach for it

    Work that's bigger than one conversation

    • A codebase-wide sweep — every route handler audited for the same class of bug
    • A 500-file migration where each file can be transformed in isolation
    • A research question worth cross-checking from several independent angles
    • A hard plan worth drafting three ways and weighing before you commit
    • Anything where you want independent agents adversarially reviewing each other's findings before they reach you
    Leave it off

    Everything routine

    • Ordinary implementation and review — /effort high is the balanced default for a reason
    • Anything latency-sensitive: every request in an ultracode session costs more and takes longer
    • Tasks needing your sign-off between stages — a run takes no mid-flight input except permission prompts
    • A first pass at an unfamiliar repo. Gauge the spend on one directory before pointing it at everything

    Drop back with /effort high when you return to routine work. It's one command, and an ultracode session won't remind you.

    The rule that generalises: start at the cheapest level that can reliably finish the work, and raise effort when the cost of a wrong judgement exceeds the cost of more reasoning. Ultracode is the far end of that trade — worth it exactly when a task is large enough that orchestration, not thinking, is the bottleneck.
    08 The off switch

    Turning workflows off

    Ultracode's orchestration half rides on dynamic workflows, so disabling workflows disables it. When they're off, the bundled workflow commands disappear, the ultracode keyword stops triggering runs, and ultracode is removed from the /effort menu.

    For yourself
    any one of these
    >/config→ toggle Dynamic workflows off
    ~/.claude/settings.json → "disableWorkflows": true
    $CLAUDE_CODE_DISABLE_WORKFLOWS=1
    For an organisation

    Set "disableWorkflows": true in managed settings, or use the toggle on the Claude Code admin settings page. The same disable settings apply on every surface — CLI, Desktop, IDE extensions, claude -p, and the Agent SDK.
